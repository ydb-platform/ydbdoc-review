## Задачи и приёмка

### F01. Контракт файлов и частей
- Результат: устойчивые ID, диапазоны исходного/защищённого текста, статус и перевод каждой части; явное отсутствие результата.

- Изменить: document.py и используемые структуры передачи результатов; зафиксировать минимальный формат для хранения, критика и исправлений.
- Удалить: передачу склеенного неполного текста как достаточного способа сопоставления частей.
- Зависимости: нет. До параллельных правок согласовать интерфейсы с F02/F04/F05.
- Приёмка: пропуск частей 0/1/3 не меняет ID/границы оставшихся; восстановление и continue сохраняют соответствие; маркеры не разрываются; публичный частичный результат явно незавершён.

### F02. Компактное хранение и чтение
- Результат: явная схема контекста, однократное хранение обращений, независимые обновления метаданных, постраничное чтение.
- Требования: §4, §7, §8–8.1.
- Изменить: store.py, адаптер записи состояния; явно перечислить сохраняемые поля. Предусмотреть понятное поведение при неподдерживаемом старом контексте, без автоматического удаления базы.
- Удалить: сериализацию всего RunResult/Candidate, индекса репозитория и дублирующих вложенных результатов; полную перезапись при поздней ошибке; выборку всего объекта одним результатом YDB.
- Зависимости: F01 (формат). Разработка может начинаться после фиксации интерфейса.
- Приёмка: при одинаковых двух документах увеличение постороннего дерева не увеличивает контекст; запрос/ответ имеет одну запись; обновление статуса не пишет заново контент; объект больше 48 МиБ читается страницами; TTL, расходы, continue и ошибки чтения корректны.

### F03. Пригодные запросы к модели
- Результат: оценка вместимости для модели, корректный output budget, поддерживаемое управление reasoning, точная диагностика.
- Требования: §3–3.1, §7.
- Изменить: model.py, config/runtime.py, config/defaults.py; проверить официальные возможности фактического провайдера. Если отключение reasoning не поддерживается, изложить варианты модели для отдельного согласования.
- Удалить: необоснованное равенство UTF-8 байт токенам; объединение length/empty/invalid-format в одну ошибку.
- Зависимости: нет.
- Приёмка: помещающийся файл не дробится искусственно; итоговый запрос учитывает промпт/глоссарий/output; reasoning-only length распознаётся и оплачивается, не считается переводом и не запускает fallback по качеству; прежние транспортные ограничения fallback соблюдены. Не заявлять совместимость с живым API без проверки.

### F04. Первичный перевод и промпт
- Результат: защита → целый файл или безопасные части → перевод → восстановление → коммит кандидата.
- Требования: §1–3.1, §5.1.
- Изменить: document.py, сборку промптов, подготовку кандидата; передавать только нужный текст и реальные правила заданного глоссария.
- Удалить: ненужный контекст чужих файлов, искусственное дробление; не удалять переводимые комментарии кода и полезные защиты.
- Зависимости: F01, F03.
- Приёмка: два документа проходят с фиксируемыми частями без пропусков/дублей; успешные ответы сохраняются при частичном сбое; не изменены правила двуязычных пар, зависимостей и механических удалений/переименований.

### F05. Критик и адресное исправление
- Результат: критик проверяет сопоставленные части; исправляются только части с замечаниями, включая явно пропущенные.
- Требования: §4, §5–5.1.
- Изменить: quality.py:review_parts, quality_loop.py:repair_document/run_quality_loop; промпты критика и исправления.
- Удалить: эвристическое угадывание соответствия неполного перевода вместо сохранённых границ; повторную отправку всех успешных частей; повторение цикла после невозможного исправления.
- Зависимости: F01, F03, F04.
- Приёмка: пропущенный чанк локализован; ремонт получает его исходник и релевантные замечания; остальные не переводятся; максимум 3 проверки/2 исправления; неизменённый кандидат не проверяется повторно без основания; стиль не самостоятельный блокер; verify/continue соблюдают свой контракт.

### F06. Полезная диагностика сборки и ссылок

- Удалить: тысячи ошибок «якорь не проверен» и ложные рекомендации заменить существующие адреса; повторную сборку прежнего кандидата.
- Зависимости: нет для адаптеров; интеграция с F05.
- Приёмка: одна ошибка сборки даёт конкретную первичную причину и сгруппированную неполную проверку якорей; RED сохраняется; реальные ошибки ссылок не скрыты; без baseline не приписываются переводу; новый SHA проверяется заново.

### F07. Описание PR и короткие отчёты
- Результат: человекочитаемый промежуточный и итоговый текст, расходы, причины и действия; подробности отдельным доступным артефактом.

### F08. Финализация без повторной работы

- Зависимости: F02, F07.
- Приёмка: отказ первого/второго отчёта и хранилища тестируются раздельно; нет новых модельных вызовов, двойного списания и полного повторного сохранения; стоимость не теряется; недоступность continue объяснена; GREEN не появляется без проверок.

- Удалить: ожидания отменённого поведения. Полезные парсеры/защиты/ошибки интеграций сохранить. Тест, обнаруживший дефект, не удалять ради зелёного CI.
- Зависимости: сценарии готовить параллельно с F02–F08; финальная интеграция после них.
- Приёмка: каждый воспроизводящий тест падает на соответствующем старом дефекте и проходит после исправления; нет исключения новых проверок из CI; весь предусмотренный набор выполнен на одном зафиксированном SHA, ограничения перечислены.

### F10. Независимая итоговая приёмка и передача

- Зависимости: F01–F09 приняты.
- Приёмка: независимый тестер не полагается на отчёт разработчика; проверены 3 режима, интеграционные ошибки, размер контекста и сообщение пользователю; реальные провайдер/GitHub/YDB явно отделены от имитаций. Принятые коммиты опубликованы в main, воспроизводимые результаты переданы пользователю; интеграцию выполняет тимлид. Пользователь разрешил публикацию в main. Production-тег без отдельного поручения не переносить.

## Параллельная работа

Сначала F01 и F03; после фиксации интерфейсов F02/F04/F06/F07 могут идти независимо. F05 следует за F04, F08 — за F02/F07. F09 готовит независимые сценарии заранее и завершает интеграцию после исправлений. F10 завершает работу. Общие файлы quality_loop.py, runner.py и структуры document.py изменять через согласованного владельца/последовательную интеграцию, а не одновременно в одном checkout.

На каждую задачу — новый разработчик с чистым контекстом, затем новый независимый тестер. При провале задача остаётся незавершённой. Лид может одновременно отдать следующую готовую задачу другому разработчику; предел — реально доступные агентные слоты и ресурсы машины. Точные правила мониторинга и восстановления — в [промпте тимлиду](independent-team-lead-prompt.md).
