# Memory Bank — согласованные решения владельца продукта

Дата: 2026-09-14. Источник: явные ответы пользователя в текущем MARS-чате.
Канон: [REQUIREMENTS_RU.md, §0](../../REQUIREMENTS_RU.md).

## D-001 — ветка и PR обязательны, затем критик

Перевод сохраняется в ветке и обычном PR до первого критика. Далее:
критик → автоматическое исправление → критик → автоматическое исправление → итоговый критик.
Если замечаний, требующих исправления, нет, цикл завершается раньше.
Максимум три смысловые проверки и два автоматических исправления.
Цель — автоматически получить корректный перевод, а не только список советов.
После третьей проверки дальнейших исправлений нет: итоговый вердикт и оставшиеся
замечания записываются в существующий PR. Плохой вердикт не отменяет PR и не
считается успешной проверкой. Предупреждения о кириллице в коде по D-003 не
запускают исправление защищённого кода.

Повторно подтверждено владельцем продукта в этом чате. Это отменяет прежнее
правило одного прохода без исправлений, появившееся в параллельной работе.

## D-004 — отдельный неизменяемый кандидат для каждой проверки

Перед каждой проверкой заканчиваются сборка полных EN-файлов и механические
исправления структуры, ссылок, навигации и форматирования. Кандидат фиксируется
в ветке отдельным SHA K1, после исправлений — K2 и K3. Во время проверки
соответствующий кандидат неизменяем. Исправления между проверками разрешены и
обязательны при исправимых замечаниях в пределах D-001. Каждая проверка читает
точные байты своего SHA; итоговый отчёт относится к последнему проверенному SHA.
После итоговой проверки нельзя менять содержимое без новой проверки.

## D-005 — полное сравнение целых смысловых блоков

Critic получает авторитетный RU и точный EN из `K` целыми предложениями или
смысловыми блоками. Каждый RU-блок и каждый сопоставленный EN-блок должны быть
покрыты ровно один раз в каждой итерации критика. Таблицы, YFM-конструкции и смешанный Markdown не могут
исчезать из проверки. Недоказанное покрытие, неоднозначное сопоставление или
потерянный блок дают RED как незавершённая проверка, а не GREEN.

## D-006 — critic и автоматическое исправление замечаний

В каждой итерации critic проверяет целые смысловые блоки текущего кандидата и
возвращает замечания; сам вызов critic не меняет его байты. Затем конвейер
автоматически исправляет замечания, фиксирует новый SHA и повторяет critic,
всего не более двух исправлений и трёх проверок (D-001).
Технические retries и fallback ограничены отдельно и не считаются смысловыми
итерациями. Отказ, пустой/невалидный ответ или исчерпанные технические ошибки
не означают GREEN. Существующий fallback переводчика сохраняется.
Специальные алгоритмы для отдельных союзов, отрицаний или конкретных фраз
не заменяют смысловую проверку. Полное покрытие блоков требуется в каждой итерации.

## D-007 — отчёт, по которому проблему можно найти глазами

Отчёт начинается с GREEN, YELLOW или RED. Для каждого замечания он показывает
точный SHA кандидата, EN-файл, реальную строку или диапазон строк, короткую
цитату из этих строк, простое описание отличия смысла и ожидаемое исправление.
Внутренние коды и идентификаторы вторичны. Если SHA, строку или цитату нельзя
доказать по байтам `K`, отчёт показывает RED о недостоверных данных и не
подставляет первую или похожую строку.

## D-002 — новая метка запускает перевод с нуля

Пользователь: «новая метка doc_translate должна удалить текущую ветку и заново запустить перевод».
Если предыдущий запуск для того же исходного PR ещё работает, сначала
остановить его и дождаться остановки, затем удалить ветку перевода и начать
новый полный запуск. Одновременно изменять ветку перевода может только один
запуск. Остановленный запуск не должен записывать коммиты или публиковать
устаревший вердикт в PR после начала нового запуска. Если остановка не
подтверждена, удаление ветки и новый перевод не начинаются; причина явно
отражается в статусе запуска. Запуски разных исходных PR этим правилом не
отменяются.

Удаляется текущая ветка перевода этого исходного PR, затем создаётся новая ветка
и выполняется полный перевод с циклом D-001. Неизменённый исходный SHA не
является причиной пропуска. Старый перевод, Analyze no-op и checkpoint не
заменяют новый полный запуск. Исходная ветка автора не удаляется.

## D-003 — В блоках кода переводятся только комментарии

Сначала определить, что блок документа является кодом, затем выделить реальные
комментарии по синтаксису его языка. Тексты комментариев переводить отдельными
запросами к модели, отдельно от основного текста документа; результат вставлять
обратно, сохраняя границы комментария и весь код вне комментариев без изменений.
Строковые литералы, идентификаторы и прочее содержимое кода не переводить.

Примеры синтаксиса комментариев: `//`, `/* ... */`, `#`, SQL `--`,
HTML/XML `<!-- ... -->`; допустимость определяется языком блока.
Маркеры внутри строковых литералов не являются комментариями. Python triple-quoted
строки сами по себе не являются комментариями и не должны переводиться как они.
Если комментарий нельзя уверенно распознать, не переписывать код наугад.

Если эвристика критика обнаружила кириллицу в блоке кода, добавить в отчёт PR
предупреждение с путём файла и номером строки для техписателя. Само наличие
кириллицы в коде не является RED, блокером или основанием менять код/запускать
ремонт. Это исключение к прежнему абсолютному запрету кириллицы в защищённых
зонах; к обычному тексту документа это исключение не относится.

Приёмка: в блоке `print("Привет") # Приветствие` меняется только комментарий;
строка `"Привет"` остаётся исходной, предупреждение указывает файл и строку.
Комментарий отправляется на перевод отдельным запросом. `//` внутри URL-строки
не извлекается как комментарий. То же правило сохранности действует для
многострочных комментариев: изменяется только их текст.

## D-008 — обычный переводной PR

Пользователь: «мне пофигу, меня устроит любой вариант тут»; просит выбрать
самый простой вариант. Выбран обычный PR (`draft=false`), без автоматического
переключения в draft по вердикту QA. Качество и готовность к merge показываются
в отчёте; обычный статус PR не означает GREEN. Это решение о требованиях,
а не подтверждение текущей реализации.

## D-009 — нет файлов для перевода

Владелец продукта подтвердил: «Да, так».

Если по исходному PR нет файлов для перевода, запуск завершается с сообщением
«Нет файлов для перевода» в исходном PR. Новая переводная ветка и переводной PR
не создаются; переводчик и критик не запускаются. Это нормальный исход без
перевода, а не подтверждение качества перевода. Это явное исключение к
обязательному созданию ветки и PR в D-001/D-002 и к запрету завершения без PR.
Пустой список должен следовать из успешно определённого состава работ:
ошибка чтения или определения файлов и решение модели «перевод уже актуален»
не являются этим случаем. При непустом составе работ действует полный запуск D-002.

Приёмка: PR только с изменениями кода вне состава переводимой документации
даёт сообщение в исходном PR без вызовов переводчика/критика и без создания
переводной ветки/PR. Ошибка получения файлов не маскируется этим исходом.

## Статус

Решения внесены в функциональные требования. Код и тесты в этой правке не
изменялись; соответствие реализации этим правилам ещё не подтверждено.
Старая оценка тестов F049/F055/F057/F088 как «неверных» только на основании
прежнего запрета публикации больше не отражает желаемый продуктовый контракт.
