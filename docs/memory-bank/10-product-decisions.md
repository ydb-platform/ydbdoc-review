# Memory Bank — согласованные решения владельца продукта

Дата: 2026-09-14. Источник: явные ответы пользователя в текущем MARS-чате.
Канон: [REQUIREMENTS_RU.md, §0](../../REQUIREMENTS_RU.md).

## D-001 — ветка и PR обязательны, затем критик

Пользователь: «ветка должна быть», «PR должен быть всегда».
Перевод полностью собирается, проходит все механические исправления, сохраняется
в отдельной ветке и PR до первого critic. После этого critic читает точный SHA
готового кандидата и не меняет его. Неточность перевода становится понятным
предупреждением для техписа, а не автоматической правкой или повторным переводом.
Ошибки QA, отказ критика и оставшиеся замечания не отменяют PR; неполная QA
отмечается явно и не может выглядеть зелёной.

Это отменяет прежнюю рекомендацию аудита withholding по качеству и прежние
publication veto в R-GL-12/13, §6.253 и связанных исторических записях.
Проверки содержимого нужны, но определяют вердикт, а не наличие PR.
Draft/обычный PR этим решением отдельно не выбирался.

## D-004 — один неизменяемый финальный кандидат

Сначала переводятся все куски прозы и собираются полные EN-файлы. Затем
заканчиваются все изменения структуры, ссылок, навигации и форматирования.
Получившееся дерево фиксируется commit SHA `K` в ветке перевода. Только после
этого запускается critic. Critic, отчёт и публикация обязаны ссылаться на один
и тот же `K`. После начала critic содержимое `K` не изменяется. Любое изменение
создаёт новый кандидат и требует новой проверки.

Fallback переводчика разрешён, когда основной переводчик не дал пригодного
ответа, включая отказ, пустой или невалидный ответ и исчерпанные транспортные
ошибки. Замечание critic не является причиной повторно вызывать переводчик.

## D-005 — полное сравнение целых смысловых блоков

Critic получает авторитетный RU и точный EN из `K` целыми предложениями или
смысловыми блоками. Каждый RU-блок и каждый сопоставленный EN-блок должны быть
покрыты ровно один раз. Таблицы, YFM-конструкции и смешанный Markdown не могут
исчезать из проверки. Недоказанное покрытие, неоднозначное сопоставление или
потерянный блок дают RED как незавершённая проверка, а не GREEN.

## D-006 — critic только проверяет

Для каждого корректно полученного пакета выполняется один смысловой запрос.
Critic не применяет предложенный текст, не запускает переводчик и не делает
второй проход после найденного замечания. Обычная неточность смысла даёт YELLOW
и совет техпису. Отказ critic, невалидный ответ или техническая ошибка после
ограниченного восстановления дают RED. Специальные правила для `and`/`or`,
отрицаний, пунктуации или конкретного LDAP-примера запрещены.

## D-007 — отчёт, по которому проблему можно найти глазами

Отчёт начинается с GREEN, YELLOW или RED. Для каждого замечания он показывает
точный SHA кандидата, EN-файл, реальную строку или диапазон строк, короткую
цитату из этих строк, простое описание отличия смысла и ожидаемое исправление.
Внутренние коды и идентификаторы вторичны. Если SHA, строку или цитату нельзя
доказать по байтам `K`, отчёт показывает RED о недостоверных данных и не
подставляет первую или похожую строку.

## D-002 — новая метка запускает перевод с нуля

Пользователь: «новая метка doc_translate должна удалить текущую ветку и заново запустить перевод».
Удаляется текущая ветка перевода этого исходного PR, затем создаётся новая ветка
и выполняется полный перевод с циклом D-001. Неизменённый исходный SHA не
является причиной пропуска. Старый перевод, Analyze no-op и checkpoint не
заменяют новый полный запуск. Исходная ветка автора не удаляется.

## D-003 — В блоках кода переводятся только комментарии

Сначала определить, что блок документа является кодом, затем выделить реальные
комментарии по синтаксису его языка. Тексты комментариев переводить отдельными
запросами к модели, отдельно от основного текста документа; результат вставлять
обратно, сохраняя границы комментария и весь код вне комментариев без изменений.
Строковые литералы, идентификаторы и прочее содержимое кода не переводить.

Примеры синтаксиса комментариев: `//`, `/* ... */`, `#`, SQL `--`,
HTML/XML `<!-- ... -->`; допустимость определяется языком блока.
Маркеры внутри строковых литералов не являются комментариями. Python triple-quoted
строки сами по себе не являются комментариями и не должны переводиться как они.
Если комментарий нельзя уверенно распознать, не переписывать код наугад.

Если эвристика критика обнаружила кириллицу в блоке кода, добавить в отчёт PR
предупреждение с путём файла и номером строки для техписателя. Само наличие
кириллицы в коде не является RED, блокером или основанием менять код/запускать
ремонт. Это исключение к прежнему абсолютному запрету кириллицы в защищённых
зонах; к обычному тексту документа это исключение не относится.

Приёмка: в блоке `print("Привет") # Приветствие` меняется только комментарий;
строка `"Привет"` остаётся исходной, предупреждение указывает файл и строку.
Комментарий отправляется на перевод отдельным запросом. `//` внутри URL-строки
не извлекается как комментарий. То же правило сохранности действует для
многострочных комментариев: изменяется только их текст.

## Статус

Решения внесены в функциональные требования. Код и тесты в этой правке не
изменялись; соответствие реализации этим правилам ещё не подтверждено.
Старая оценка тестов F049/F055/F057/F088 как «неверных» только на основании
прежнего запрета публикации больше не отражает желаемый продуктовый контракт.
