# Memory Bank — финальная смысловая проверка кандидата

> Действующий контракт. Он уточняет D-001/D-004–D-007 в
> [функциональных требованиях](../../REQUIREMENTS_RU.md) и заменяет прежний
> запрет автоматических исправлений: владелец продукта повторно подтвердил цикл critic → fix → critic → fix → critic.

## 23. Четыре независимых задачи реализации

### 23.1. Финальный кандидат и порядок стадий

Перед каждой проверкой заканчиваются сборка полных EN-файлов и механические
исправления структуры, ссылок, навигации и форматирования. Кандидат фиксируется
в ветке отдельным SHA K1, после исправлений — K2 и K3. Во время проверки
соответствующий кандидат неизменяем. Исправления между проверками разрешены и
обязательны при исправимых замечаниях в пределах D-001. Каждая проверка читает
точные байты своего SHA; итоговый отчёт относится к последнему проверенному SHA.
После итоговой проверки нельзя менять содержимое без новой проверки.

PR создаётся до первой проверки и сохраняется при любом вердикте.
Приёмка через production entrypoint проверяет порядок вызовов, SHA каждой
проверки, раннее завершение и сохранность PR при оставшихся замечаниях.

### 23.2. Полное покрытие смысловых блоков

Из frozen RU authority и EN `K` строится общий список целых смысловых блоков с
устойчивыми идентификаторами, путями и строками. Каждый RU-блок и каждый
сопоставленный EN-блок проверяются ровно один раз в каждой итерации. Пакетирование группирует
блоки, но не режет их посередине. Обычные
абзацы, списки, YFM-контейнеры, таблицы и смешанный Markdown не пропускаются.
Пустой документ отличается от ошибки извлечения. Потеря или дублирование
доставленного текста дают RED `incomplete review`. Повторяющиеся разделы без
якорей сопоставляются по порядку; смысловое соответствие оценивает модель.

TDD-приёмка включает YFM-only, GFM/YFM tables, mixed Markdown, длинный блок,
дубликаты, missing target и реальный абзац PR #53007, где `bind_dn` и
`bind_password` были ошибочно превращены из обязательной пары в альтернативы.

### 23.3. Критик и автоматические исправления

Перевод сохраняется в ветке и обычном PR до первого критика. Далее:
критик → автоматическое исправление → критик → автоматическое исправление → итоговый критик.
Если замечаний, требующих исправления, нет, цикл завершается раньше.
Максимум три смысловые проверки и два автоматических исправления.
Цель — автоматически получить корректный перевод, а не только список советов.
После третьей проверки дальнейших исправлений нет: итоговый вердикт и оставшиеся
замечания записываются в существующий PR. Плохой вердикт не отменяет PR и не
считается успешной проверкой. Предупреждения о кириллице в коде по D-003 не
запускают исправление защищённого кода.

В каждой итерации critic проверяет целые смысловые блоки текущего кандидата и
возвращает замечания; сам вызов critic не меняет его байты. Затем конвейер
автоматически исправляет замечания, фиксирует новый SHA и повторяет critic,
всего не более двух исправлений и трёх проверок (D-001).
Технические retries и fallback ограничены отдельно и не считаются смысловыми
итерациями. Отказ, пустой/невалидный ответ или исчерпанные технические ошибки
не означают GREEN. Существующий fallback переводчика сохраняется.
Специальные алгоритмы для отдельных союзов, отрицаний или конкретных фраз
не заменяют смысловую проверку. Полное покрытие блоков требуется в каждой итерации.

Приёмка: сценарии без замечаний, исправление после первого и второго прохода,
остаточные замечания после третьего; отсутствие третьего исправления; каждый
critic получает новый актуальный SHA после изменения. Проверки должны вызывать
реальный orchestration entrypoint с fake LLM, а не проверять строки исходника.

### 23.4. Отчёт по exact candidate

Все поверхности итогового отчёта используют результат последней проверки и её `K`.
Видимый порядок полей: статус, EN path, строка/диапазон, короткая цитата из raw
bytes `K`, понятная проблема, ожидаемое исправление. Внутренние category, block
ID и сведения о модели показываются только как вторичная диагностика.

Строка подтверждается точным block evidence. Если подсказка устарела, допустима
повторная локализация только внутри того же блока и только при единственном
совпадении. SHA mismatch, missing block, неоднозначность и недостоверная цитата
дают RED report-integrity без выдуманной строки или fallback на начало файла.

TDD-приёмка включает exact #53007 line 104, сдвиг строки после finalization,
повторяющийся текст, multiline/CRLF, несовпадающие SHA и единый результат в PR
body, полном отчёте и source handoff.

## 24. Граница с существующим поведением

PR #169–#173 остаются доставленными защитами fallback coverage, fail-closed
refusal recovery, label spacing и fragment reconciliation. Новый контракт не
отменяет bounded translator/critic recovery и детерминированные structural gates.
Он меняет только место и роль смыслового critic в `doc_translate`: critic идёт
после сборки каждого `K`; между проверками конвейер автоматически исправляет
замечания в пределах двух попыток и фиксирует новый кандидат.

Standalone `doc_verify` нужен после ручного изменения ветки или для отдельной
verify-only операции. Повторно ставить `doc_verify` сразу после обычного
`doc_translate` не нужно, потому что финальная проверка уже встроена в job.

## Уточнение простоты проверки — 2026-09-15

По указанию владельца продукта критик сравнивает RU/EN файл или чанк.
Для неизменённых границ допустима группировка в порядке документа; одинаковая
форма соседних разделов без якорей не запрещает смысловую проверку.
Полнота плана означает полноту переданного текста, а не доказанное совпадение
смысла. Перестановки и ошибки перевода оценивает модель. Прежнее требование
уникальной формы каждого неякорного раздела отменяется; потеря отправленного
содержания, несовпадение SHA и незавершённый ответ по-прежнему не дают GREEN.

Критик имеет отдельный бюджет `critic_batch_chars`. Навигационный YAML проверяется
по собственному результату и точным байтам SHA, без требования прозаического
ReviewPlan. Замечание обязано объяснять проблему; готовый `suggested_text`
необязателен. Техническая ошибка незавершённой проверки отображается один раз.
До проверки подготовка строит legacy-цитаты только для manual actions;
финальный критик формирует свои координаты по проверенному SHA.

## 26. Повторная работа и лимиты тестов — 2026-09-15

Полный offline replay #51079 проверяет реальную сборку и не отключается из-за
таймаутов. Подготовка использует production prepare-only профиль; проверки
неверного текста, отказов модели, SHA и отсутствия сетевых вызовов сохранены.
Каждый тест вместе с фикстурами ограничен 10 секундами.

Повторные чистые операции над одинаковыми байтами переиспользуют ограниченные
кеши с неизменяемыми значениями; публичные изменяемые результаты создаются заново.
Проверка существования страниц TOC читает список путей фиксированного SHA,
а для проверки include продолжает читать содержимое. Поиск include прекращается
после доказанной достижимости всех проверяемых страниц. Если все проверяемые
входящие якоря сохранены, повторный обход остальных EN-страниц не требуется.
Проверка duplicate anchors разбирает настоящие Markdown-заголовки, включая
entities и escapes; сравнение сырого текста якорей не заменяет parser.

Git-read cache ограничен снимком проверки. Изменяемые overlay-файлы читаются
заново. Выделение одной ссылки для диагностики сохраняет номер строки без
копирования всего документа для каждой ссылки. Статус GREEN не запускает
новый перевод из-за информационных замечаний.

Финальный языковой gate сначала проверяет наличие кириллицы по прежнему
Unicode-предикату. При её отсутствии разбор Markdown не нужен; при наличии
разбираются границы блоков, чтобы исключить код и сохранить номера строк.

## 27. Provenance после автоматического исправления — 2026-09-15

Запуск #51079 `34953927265` создал K2, затем упал до второго критика:
`bind_translation_artifact` ошибочно требовал прямого родителя P у K2.
Корневой C остаётся K1 и сохраняет проверенную связь с P; K2/K3 проверяются
через `validate_authority_evidence` как потомки C до push. RU-authority
не меняется. Coverage evidence пересоздаётся для текущего K, итоговый отчёт
относится к последнему проверенному K.

Регрессия production entrypoint использует настоящую проверку provenance
вместо заглушки, Git-коммиты и проверку evidence итогового PR; покрывает
открытый и слитый исходный PR, одно/два исправления и исчерпание попыток.

## 28. Итоговый статус после исправления — 2026-09-15

Расширенная регрессия требует GREEN после устранения замечаний и YELLOW
после исчерпания двух исправлений с оставшимися обычными замечаниями.
Это выявило две независимые причины ложного RED:

- PR-body ошибочно требовал C == K. Теперь корень C допускается только при
  подтверждённом Git ancestry C → K; неизвестный/посторонний C остаётся
  конфликтующим SHA и даёт RED на всех поверхностях отчёта. Ссылки отчёта
  по-прежнему обязаны указывать на K.
- Проверки после repair читали worktree с нормализацией CRLF и ошибочно
  сообщали `report_checkout_mismatch`. Они используют существующий
  `_final_tree_reader`: точные байты объявленных overlays и frozen K для
  остальных путей, с сохранением tombstones.

Приёмка: реальные Git-коммиты, CRLF, открытый/слитый источник, GREEN/YELLOW
итогового PR и прежние negative report-integrity tests.
