# Причины неудачного перевода PR 51079 → PR 53522

Проверены GitHub PR и diff, завершённый Actions run 35358140073, исходный код Action на SHA `54a37c42ebb620106b3c72f727edf5d446c1d3ec`, записи YDB запуска `f20b3989fe274605b8815e3163a95101`. Проверенный и опубликованный кандидат: `d95f9c71176a2f75ddd788651deb9505274b713b`. Данные YDB читались отдельным диагностическим workflow без записи в базу. Производственный код и PR не изменялись.

## Вывод

RED обоснован: два файла переведены частично, пропали начальные разделы и защищённые конструкции, повреждён YFM, критик не выполнил ни одного обращения. Но объяснение пользователю сломано: описание PR — техническая заглушка, подробный комментарий GitHub отклонил из-за превышения размера. Стоимость сохранена, но видна только в исходном PR.

## 1. Что случилось с переводом

`auth_config.md` разбит на 6 частей. Части 0, 1 и 3 не получили пригодного ответа; опубликованы части 2, 4, 5. `authentication.md` разбит на 8 частей: не получены 0, 1, 3, 5, 6; опубликованы 2, 4, 7.

Все 14 обращений выполнены последовательно к `deepseek-v32`. Восемь неудачных ответов: HTTP 200, `finish_reason=length`, пустой `content`, непустой `reasoning_content`, ровно 8000 выходных токенов. Модель исчерпала выходной бюджет на рассуждения, не выдав перевод. Всего usage: 23212 входных и 93102 выходных токена. В сохранённых ответах 264689 символов reasoning и 19014 символов непосредственно перевода.

Транспорт корректно не принял reasoning за перевод и не запустил fallback: это не timeout/сеть/5xx, для которых §3 разрешает альтернативу. Ошибка — неподходящие настройки продуктивного запроса и неинформативная диагностика `Model returned no usable text or invalid response JSON`, которая не различает невалидный JSON и исчерпание лимита на рассуждения.

`config/defaults.py:default_runtime_data` задаёт 32768 context / 8000 output; `config/runtime.py:load_runtime` считает UTF-8 байты как верхнюю оценку токенов. Из-за консервативной оценки запросы разбиваются на небольшие части: реальные входы примерно 1–2 тысячи токенов. `model.py:ModelClient.chat` не задаёт управление reasoning. Точный выигрыш от других настроек требует отдельной проверки; обещать конкретное ускорение без запуска нельзя.

`document.py:translate_document` сохраняет доступные части и ставит unfinished. Отсутствующие части не восстановлены, поэтому опубликованные файлы начинаются с середины текста. Публикация частичного результата в draft предусмотрена §6; она сама по себе не является нарушением. Нарушение — отсутствие пригодного объяснения неполноты и невозможность завершить проверку/исправление.

## 2. Почему нельзя мержить

| Проверка | auth_config.md | authentication.md |
|---|---:|---:|
| Заголовки, исходник → перевод | 10 → 3 | 31 → 8 |
| Абзацы | 126 → 48 | 144 → 43 |
| Пункты списков | 23 → 6 | 64 → 20 |
| Блоки кода | 8 → 4 | 2 → 0 |

Разница числа абзацев сама по себе не доказывает потерю — это прямо сказано в §5. Здесь потеря подтверждена отсутствием ответов для конкретных частей и фактическим содержимым файлов.

Автоматические проверки обнаружили:
- исчезновение/изменение защищённых частей и кода;
- `Unmatched YFM table delimiter` в auth_config.md, строка 36 опубликованного файла;
- `Unclosed YFM note` в authentication.md;
- незавершённую проверку критиком: `Cannot establish corresponding critic units within request budget; full review incomplete`.

`quality.py:review_parts` не может сопоставить сильно неполный перевод с исходником в установленном бюджете. Все три раунда имеют пустые `parts` / `completed_parts`; платных обращений критика нет. Все четыре попытки подготовки исправлений (два файла × два раунда) также закончились `CapacityError` в `review_parts`, с пустым списком частей; модель не вызывалась. Все три проверки относятся к одному SHA — исправленного кандидата между раундами не появилось.

Три сборки завершились ошибкой. Полный лог первого раунда установил первичные ERR:
- `Note must be closed in en/security/authentication.md`;
- `YFM005 / block-not-closed`, строка 36: `{% note info %}` не закрыт;
- `MD032 / blanks-around-lists`, строка 91: нет необходимого отделения списка пустыми строками.

Сборщик публикует путь без `core`; в исходном дереве это `ydb/docs/en/core/security/authentication.md`. Предупреждения YFM в других статьях указывают на отсутствующие заголовки/якоря auth_config и authentication. Полный лог сохранён в `yfm_full.log`.

 Сам YFM работал 45,378 / 43,728 / 42,784 секунды. Проверяется весь набор документации, а не только два файла. Итог содержит 8894 замечания по 1148 путям; 8876 имеют тип links; среди них замечания к README и другим файлам вне перевода. Нельзя приписывать весь этот список изменениям PR: необходима классификация ошибок по происхождению и проверка на исходном SHA. Базовый SHA в рамках этого расследования отдельно не собирался.

Из 8876 сообщений типа links: 8195 — якорь не проверен из-за неуспешной сборки; 635 — отсутствующая цель ссылки; 30 — пустой include; 7 — отсутствующий include; 8 — ссылка из EN на RU; 1 — отсутствующий asset. 8195 сообщений — каскад одного общего сбоя сборки, а не столько же доказанных дефектов перевода. Код `links.py:check_links` создаёт отдельную ошибку на каждый якорь, когда `build.ok_for()` ложно, и советует чинить URL вместо устранения первичного сбоя сборки. Это делает рекомендации вводящими в заблуждение.

## 3. Куда делись отчёт и стоимость

`publication.py:Publisher.publish` создаёт PR с телом `RED\nChecked SHA: ...`. Это постоянное описание: дальнейшего обновления тела PR нет.

`report.py:render_reports` действительно формирует подробный отчёт со стоимостью, но `create_reporter` отправляет его отдельным комментарием. Перед отправкой `runner.py:finalize` синхронно вызывает `RunStore.save`.

В 18:40:46 МСК краткий комментарий в исходном PR опубликован. Следующий POST в `/issues/53522/comments` получил HTTP 422: `Body is too long (maximum is 65536 characters)`. Все 8894 замечания собираются в один текст без ограничения общего размера, группировки или вынесения полной диагностики. Поэтому в переводном PR нет ни объяснения RED, ни стоимости.

| Статья | Стоимость |
|---|---:|
| Первичный перевод | 86,0876 ₽ |
| Критик | 0 ₽ |
| Исправления | 0 ₽ |
| Итого | 86,0876 ₽ |

Из суммы 58,6170 ₽ приходятся на восемь ответов без пригодного перевода. Они оплачиваются и по §7 должны учитываться. Повторное сохранение не создало повторного списания: ledger использует стабильные ключи обращений. Источник суммы — сохранённый usage и тарифы Action, не отдельный счёт облачного биллинга.

| Этап | Время | Наблюдение |
|---|---|---|
| Подготовка runner / checkout | 17:44:53–17:50:37 | Полный checkout большого YDB; workflow использует fetch-depth: 0 |
| Сборка Docker | 17:50:37–17:51:38 | Около минуты |
| Снимок / план до первого запроса | 17:51:38–17:52:47 | Около минуты |
| Первичный перевод и промежуточное сохранение | 17:52:47–18:23:26 | 14 последовательных вызовов, примерно 30 мин 39 с |
| Проверки до публикации PR | 18:23:26–18:28:54 | Три сборки, обход ссылок, неудачная подготовка критика/исправления |

Интервалы между обращениями включают синхронные записи в YDB: в модели данных нет отдельного точного времени окончания HTTP. Поэтому нельзя называть весь интервал чистым временем inference. Но пустые ответы с большими reasoning и заполненным output budget подтверждены сохранёнными ответами провайдера.

## 5. Почему финализация такая тяжёлая

`store.py:RunStore.save` сериализует целиком `RunResult`, включая `Candidate.entries` всего репозитория (154147 записей), кандидат внутри quality, три набора результатов сборки/ссылок, исходные документы и повторённые записи запросов/ответов. Контекст получился 108518207 байт; повторное сохранение после ошибки отчёта — 108519065 байт. Каждый разбит на 207 частей по 512 КиБ, записываемых последовательно отдельными транзакциями плюс manifest.

После ошибки отчёта `finalize` повторяет весь `save`, а не только небольшой итоговый статус. Обе генерации контекста остались в YDB до TTL.

Дополнительный подтверждённый дефект: `YDBStore.get → _parts` читает весь объект одним SQL-запросом. Реальное чтение этого контекста завершилось `Query result size limit exceeded (108519440 > 50331648)`. Для анализа пришлось читать части порциями. Значит, обещанный `doc_continue` на данном контексте штатным путём не сможет его прочитать, хотя запись существует и TTL не истёк.

## 6. Расхождения со спецификацией

- §3: получен неполный перевод. Он корректно помечен незавершённым; автоматические fallback по ошибке содержимого добавлять нельзя.
- §5: критик не охватил документы; подготовка частей не справилась с реальной неполнотой. RED корректен, но требуемая содержательная проверка/локализация не выполнена.
- §6: отсутствует подробный читаемый отчёт в переводном PR. Заглушка и отклонённый комментарий не выполняют контракт.
- §7: учёт расходов работает, но требование показать стоимость в обоих отчётах не выполнено.
- §4/§8: контекст записан, но штатно не читается из-за размера. Продолжение фактически сломано.
- §9: тесты не выявили ограничения размера комментария GitHub, размера результата YDB и реальное поведение выбранной reasoning-модели. Успешные проверки с маленькими фикстурами не подтверждали готовность к этому запуску.

Спецификация не задаёт SLA времени и не требует параллельных обращений. Само по себе время 67 минут не нарушает отдельный лимит спецификации. Причины длительности — настройки модели и избыточная финализация, а не необходимость переводить два файла час.

## 7. Порядок исправлений

1. Исправить доставку отчёта: короткий понятный итог и расходы должны быть доступны независимо от размера полного списка проблем; подробности вынести в отдельный артефакт/части с проверкой ограничений GitHub. Согласовать описание PR и комментарий.
2. Сохранять компактный контекст для продолжения, без индекса всего репозитория и повторов. Читать большие объекты постранично. Поздний сбой отчёта должен менять только итоговый статус, не перезаписывать весь контекст.
3. Настроить запросы к выбранной модели с учётом reasoning и выходного бюджета. Различать пустой ответ, length и ошибку JSON в диагностике. Не ослаблять правило fallback.
4. Сделать проверку/исправление неполных документов по известным диапазонам частей, без повторного угадывания соответствия исходника и обрывка. Проверить на точно воспроизведённых 6/8 частях этого запуска.
5. Разобрать ошибки YFM и ссылок, отличить исходные проблемы/ошибки валидатора от внесённых переводом. Не объявлять GREEN отключением проверок.
6. Добавить регрессии на реальный масштаб: пустой content с reasoning и length; частичные файлы; большой отчёт; контекст больше лимита одной выборки; ошибка публикации после успешного сохранения.
