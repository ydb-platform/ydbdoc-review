## Сценарии и владельцы

Точные варианты входов и наблюдаемый результат перечислены в [catalog.json](catalog.json). `tests: []` означает отсутствие подтверждённого продуктового теста. При реализации заменить pending на implemented и записать реальные pytest nodeids; не считать skip покрытием.

## Независимые fixtures и trace

`adapters.py` имитирует только model/GitHub/store/build. Временный Git настоящий. Нет mock для run_translate/run_verify/publish_result. Store не реализует TTL, бюджет или продолжение. Build fake не доказывает реальную сборку.

Trace — список словарей в порядке фактических обращений: `event` плюс аргументы. `model.call` хранит role/provider/round/chunk/messages/response/error/cost_rub; логический раунд отличен от чанка и технической попытки. Стоимость — Decimal RUB либо None для неизвестной. GitHub хранит base/head/draft и адресата/текст отчёта; store — table/key/value; build — SHA/status. Для продуктовой приёмки дополнительно сравнивать реальные bytes через `git show <SHA>:<path>` и SHA опубликованного/проверенного кандидата. Все assertions выполняет конкретный pytest-тест; универсального runner нет.

`test_fixture_support.py` проверяет только тестовые средства. `test_modes.py` — явно пропущенные точки будущих настоящих E2E, не заглушки успешного результата. Сеть блокирует pytest-socket; секретные переменные удаляются в contract fixtures. Ни один live client не создаётся.

## Unresolved

Не подставлять legacy ответы. Вопросы §6 рабочего анализа:
1. **Q1 — расходование трёх продолжений:** считается каждый допущенный запуск или только завершённый? Как считать отказ до модели и техническое прерывание? Требование говорит «максимум три», но не задаёт момент расходования; старое «только успешные» не принимается автоматически.
2. **Q2 — сборочная интеграция и scope вспомогательных файлов:** какая команда/config или check является обязательной сборкой нужного SHA? Как трактовать PR только с TOC/YAML и недостающие include-файлы: §1 явно описывает Markdown-ссылки, а §5 требует собираемый результат. Автоматические TOC/redirect миграции не подразумеваются.
3. **Q3 — стоимость:** откуда брать подтверждённую стоимость неудачной оплаченной попытки без usage; какие тарифы применять и к какому дню относить запуск, пересёкший московскую полночь? Не выдавать ноль за известную стоимость.
4. **Q4 — выбор продолжения и недостаточные пары:** как разрешать инструкцию без явных путей при нескольких возможных файлах; какой вывод нужен verify для RU без EN/EN без RU? Не вводить первичный перевод в verify. При одной и той же исходной/проверяемой PR согласовать компактное размещение двух видов отчёта.
5. **Q5 — fork и ошибка до появления результата:** как предоставляется запись в source head открытого fork PR; что делать при continue после прерывания до создания PR? Требования запрещают незаметно менять base и требуют существующий PR для продолжения, но не описывают эти варианты полностью.

Дополнительно из ревью: если существующий PR технически недоступен для записи, способ доставки результата должен быть согласован; самовольный fixup не разрешён.
