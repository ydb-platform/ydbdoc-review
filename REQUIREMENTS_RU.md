# Канонические требования к переводу документации

Этот файл задаёт полный действующий контракт `doc_translate`, `doc_continue` и `doc_verify`. Другие документы могут описывать устройство или историю проекта, но не добавляют требований к этим режимам.

## 1. Снимок и исходный набор

- Запуск фиксирует один неизменяемый снимок текущей базовой ветки. По нему принимаются все решения о наличии и содержимом RU- и EN-файлов.
- Исходный pull request задаёт только начальный список добавленных и изменённых RU Markdown-файлов. Изменения EN в исходном pull request не меняют направление: если одновременно изменены RU и EN, перевод выполняется с RU на EN.
- Исторически удалённые RU-файлы не входят в начальный список. Историческое удаление RU-файла никогда автоматически не удаляет и не перезаписывает актуальный EN-файл.
- Путь из начального списка участвует в запуске только при наличии RU Markdown-файла в зафиксированном снимке.

## 2. Единственное расширение набора

- Набор рекурсивно расширяется только внутренними Markdown-ссылками из уже выбранных RU-файлов.
- RU-цель ссылки добавляется, только если соответствующий EN-файл отсутствует в том же снимке.
- Повторные и циклические ссылки дедуплицируются.
- Начальные файлы не расходуют лимит. Допускается не более 20 дополнительных файлов.
- Других причин расширять набор нет.

## 3. Ограничение до вызова модели

- До создания клиента модели вычисляется сумма количества необработанных символов во всех выбранных, существующих RU Markdown-файлах.
- Максимум равен `250000` символов.
- Превышение лимита завершает запуск с вердиктом RED. Модель не вызывается, файлы не изменяются и переводной pull request не создаётся.

## 4. Перевод файла

Каждый выбранный файл обрабатывается независимо и полностью:

1. Прочитать текущие RU-байты из зафиксированного снимка.
2. Заменить защищённые структурные атомы уникальными маркерами.
3. Передать всю естественно-языковую прозу файла модели одним логическим запросом.
4. Вернуть защищённые атомы на точные места.
5. Проверить восстановленный документ.

Защищёнными атомами считаются структурные и исполняемые части Markdown и YFM, адреса ссылок, идентификаторы, код и конфигурационные значения. Естественно-языковой текст не становится защищённым только из-за своего расположения. В тот же запрос обязательно входят переводимые комментарии в коде, подписи Mermaid и значения `title` и `description` во front matter.

Существующий EN-текст не передаётся модели, не используется как шаблон и не служит источником частей результата.

## 5. Ошибки модели

- После основного провайдера допускается ровно один вызов одной настроенной альтернативы.
- Альтернатива разрешена только при фактическом timeout, сетевой ошибке, ответе HTTP 5xx или подтверждённой недоступности провайдера либо модели.
- Пустой, malformed или не прошедший проверку содержимого ответ делает файл RED. Такой ответ не запускает повтор и не разрешает переход к альтернативе.
- Других повторных попыток перевода нет.

## 6. Продолжение и проверка

- `doc_continue` является новым полным запуском по тем же правилам. В запрос модели добавляется контекст технического писателя из команды продолжения.
- `doc_continue` не использует сохранённый перевод, частичный результат или состояние прошлого запуска.
- `doc_verify` проверяет уже существующий EN-текст. Он не вызывает перевод и не изменяет EN через переводческую модель.

## 7. Валидация и публикация

- После восстановления проверяются сохранность защищённых атомов, структура Markdown/YFM и допустимость содержимого.
- Структурно небезопасный результат файла не записывается.
- Если хотя бы один выбранный файл небезопасен, безопасные результаты остальных файлов записываются и публикуются в draft translation PR с общим вердиктом RED.
- Переводной artifact не создаётся только тогда, когда после отбрасывания небезопасных результатов нет безопасного изменения для публикации.
- Связанный asset публикуется только вместе с принятой безопасной страницей, которой он принадлежит.

## 8. Отчёт и комментарий

- Отчёт показывает итоговый вердикт и ошибки по файлам понятным языком.
- Комментарий в исходном pull request содержит только ссылку на translation PR, если он создан, итоговый вердикт и стоимость запуска.
- Подробности по файлам размещаются в translation PR, а не в исходном pull request.

## 9. Явно исключённые механизмы

В контракт не входят: расширение из `main`, `TOC`, `include`, `inbound` или `fragment`; `provenance` и `reconciliation`; `coverage`; `checkpoint` и `resume`; повторное использование старого EN; differential merge; batching и resplit; content retry; статусы `WITHHOLD`; правила `R-GL`.

## 10. Приёмка

Реализация соответствует контракту, только если тесты подтверждают все следующие случаи:

- историческое удаление RU не удаляет актуальный EN;
- одновременное изменение RU и EN переводится с текущего RU;
- рекурсивно добавляются только отсутствующие EN-аналоги внутренних RU Markdown-целей и не более 20 файлов;
- лимит `250000` считается по исходным символам до создания клиента модели;
- один файл создаёт один логический запрос со всей переводимой прозой;
- старый EN и результат прошлого запуска не участвуют в создании нового EN;
- альтернатива вызывается один раз и только для разрешённых инфраструктурных ошибок;
- пустой, malformed и содержательно невалидный ответ немедленно делает файл RED;
- небезопасный файл не записывается, безопасные соседи публикуются в draft RED, а asset не отделяется от принятой страницы;
- `doc_verify` не переводит;
- комментарий исходного pull request содержит только три разрешённых элемента.
