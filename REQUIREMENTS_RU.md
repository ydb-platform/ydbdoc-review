# Требования к переводу документации

Действующий контракт `doc_translate`, `doc_verify` и `doc_continue`. Цель — простой конвейер перевода, проверки и исправления. Другие документы не добавляют требований. Этот документ описывает ожидаемое поведение, а не подтверждает его реализацию.

## 1. Исходный PR и план перевода

Для открытого PR фиксируем SHA его исходной ветки (`head`), читаем из него исходные файлы и зависимости. Наличие этих файлов в `main` не требуется. Для слитого PR используем зафиксированный снимок текущей базовой ветки. Весь запуск работает с выбранным неизменяемым снимком.

`doc_translate` до создания клиента модели определяет изменения по парам RU/EN: только RU → перевод на EN; только EN → перевод на RU. Если исходный PR уже содержит соответствующие изменения обеих версий страницы, пара пропускается без перевода и критика. Старый перевод в базе сам по себе не означает пропуск. В смешанном PR обрабатываются оставшиеся одноязычные пары. Если работы нет — «Перевод не требуется», без модели, изменений файлов и нового PR. Ошибка чтения списка файлов не означает отсутствие работы.

Изменения зеркальны: добавление → добавление перевода, изменение → обновление перевода, удаление → удаление перевода, переименование → переименование перевода. Чистые удаления и переименования выполняются без модели, но публикуются; изменения содержимого при переименовании переводятся. Если обе языковые версии уже удалены или переименованы самим PR, повторять действие не нужно. Удалённый файл читать для перевода не требуется. Если существующий выбранный исходник невозможно прочитать из снимка — RED до модели с путём и причиной.

До перевода составляем план. Если статья A ссылается внутренней Markdown-ссылкой на статью B того же языка, а перевода B на целевой язык нет, добавляем B в план: ссылка из перевода A должна вести на существующую статью. Для добавленных статей повторяем проверку. Каждый файл учитывается один раз, циклы не вызывают повторов. Пропущенные двуязычные пары не возвращаются в план через зависимости. Это правило действует для RU→EN и EN→RU.

## 2. Лимиты и доступ

Настройки берутся из Actions variables репозитория `ydb-platform/ydb`:

| Переменная | Назначение |
| --- | --- |
| `YDBDOC_MAX_DEPENDENCY_FILES_PER_ARTICLE` | Максимум дополнительных зависимых статей. Несмотря на имя, лимит общий для всего запуска и обоих направлений; исходные файлы PR не входят. Согласованное значение — 20 |
| `YDBDOC_MAX_SOURCE_CHARACTERS` | Общий максимум необработанных символов исходных Markdown-файлов плана после раннего отбора и добавления зависимостей, до замены атомов маркерами. Согласованное значение — 250000 |
| `YDBDOC_ALLOWED_ACTORS` | Разрешённые GitHub-логины для всех трёх режимов, через запятую; окружающие пробелы удаляются |
| `YDBDOC_DAILY_BUDGET_RUB` | Дневной бюджет всех трёх режимов в рублях (§7) |

Значения лимитов читаются из переменных, не фиксируются в коде. Превышение лимита зависимостей или символов даёт RED до создания клиента модели, без изменений файлов и переводного PR. План нельзя молча обрезать. Сообщение содержит фактический объём, лимит, имя переменной и понятное действие:

- Зависимости: «Перевод не запущен: требуется N зависимых статей, лимит — L (`YDBDOC_MAX_DEPENDENCY_FILES_PER_ARTICLE`). Сначала переведите часть зависимых статей отдельным PR или увеличьте переменную в настройках Actions репозитория ydb-platform/ydb». Далее — обнаруженные зависимые пути, включая превысившие лимит.
- Символы: «Перевод не запущен: объём исходных текстов — N символов, лимит — L (`YDBDOC_MAX_SOURCE_CHARACTERS`). Разделите изменения на несколько PR или увеличьте переменную в настройках Actions репозитория ydb-platform/ydb».

Доступ проверяется до изменений и модели. Пользователь вне `YDBDOC_ALLOWED_ACTORS` получает понятный отказ. На момент согласования список: `sintjuri,SixOnMyface, nataliaboldyreva,ayakivosklznak`; источником настройки остаётся переменная.

## 3. Первичный перевод и ошибки модели

Каждый файл переводится независимо: прочитать исходник → заменить защищённые атомы уникальными маркерами → перевести текст → восстановить атомы → проверить документ. При первичном переводе старый текст целевого языка не используется как шаблон или источник результата; это не ограничивает проверку и исправление существующего перевода в `doc_verify` и `doc_continue`.

Защищаем структуру и исполняемые части Markdown/YFM, адреса ссылок, идентификаторы, код и конфигурационные значения от произвольного изменения. Переводимые комментарии кода, подписи Mermaid и front matter `title`/`description` переводятся. Адреса ссылок изменяются целенаправленно по правилам языка и существования цели (§5), а не произвольно при переводе прозы.

Если текст помещается в запрос модели, отправляем целиком. Иначе разбиваем на чанки по границам разделов, абзацев или предложений; маркер неделим, граница чанка не может проходить внутри него. Чанки переводятся отдельными запросами и собираются в исходном порядке без пропусков и дублирования. Проверяем сохранность, кратность и порядок маркеров перед восстановлением атомов. Разбиение не отменяет общий лимит символов.

Для каждого обращения после основного провайдера разрешён максимум один вызов одной настроенной альтернативы — только при timeout, сетевой ошибке, HTTP 5xx или подтверждённой недоступности провайдера/модели. Других технических повторов нет. Полученный текст с повреждёнными маркерами, разметкой или содержанием поступает в общий ограниченный цикл исправлений; качество ответа само по себе не запускает fallback. Если текста нет или ответ невозможно использовать как результат, файл остаётся незавершённым, общий статус — RED. Ошибка ответа критика не считается успешной проверкой.

### 3.1. Размер запроса, промпт и идентичность частей

Размер запроса оценивается с учётом токенизации выбранной модели, промпта, глоссария и резерва для ответа. Число UTF-8 байт не принимается за число токенов без обоснования для модели. Сначала пытаемся перевести защищённый файл целиком; число чанков определяется вместимостью, а не фиксированным числом частей.

Каждый файл и чанк имеют устойчивые идентификаторы, границы исходного и защищённого текста, собственный результат и статус. Это соответствие сохраняется при сборке, проверке, исправлении и продолжении. Отсутствующий ответ остаётся явно отсутствующей частью: последующие части не сдвигают соответствие исходника и перевода. Сопоставление нельзя заново угадывать по сходству склеенного неполного текста.

Промпт перевода объясняет: это техническая документация YDB; нужно перевести данный текст, сохранить смысл, полноту и плейсхолдеры, не добавлять утверждений. При заданном глоссарии передаются необходимые термины и правила из него; одна ссылка не заменяет содержимое, если модель не умеет её читать. Источник глоссария должен быть явно установлен, выдумывать его нельзя.

Для перевода отключаются рассуждения модели, если провайдер поддерживает такой режим. Если модель не позволяет получать пригодный перевод в заданных пределах, выбор подходящей модели согласовывается отдельно; скрытой замены модели нет. Диагностика различает пустой ответ, исчерпание выходного лимита (в том числе на рассуждения) и некорректный формат. Рассуждения не принимаются за перевод. Это не расширяет условия fallback из §3.

## 4. Режимы и продолжение

- **`doc_translate`** выполняет первичный перевод и общий цикл проверки (§5). Для открытого исходного PR новый переводной PR направляется в его исходную ветку; для слитого — в базовую ветку (`main`). Так новые статьи и зависимости исходного PR доступны при проверке перевода.
- **`doc_verify`** проверяет существующие пары в PR строго в направлении RU→EN. Первичного перевода нет; сразу запускается тот же цикл критика и исправлений, что после `doc_translate`. Исправляется EN, RU служит оригиналом. Изменения и вердикт публикуются в проверяемом PR, отдельный переводной PR не создаётся. Пропуск двуязычных пар из §1 относится к `doc_translate`, а не к `doc_verify`.
- **`doc_continue`** продолжает предыдущую работу с инструкцией техписа из комментария `/ydbdoc continue <текст>` и запускается меткой `doc_continue`. Использует сохранённые переводы и замечания, исправляет только проблемные или явно указанные техписом файлы. Успешные неизменённые файлы повторно не переводятся. Исправления и новый вердикт идут в существующий PR; ветка и PR не удаляются. Для затронутых файлов действует общий цикл; ссылки и сборка проверяются для итогового результата.

Для простого продолжения сохраняем SHA исходного и проверяемого PR по завершении запуска. Если перед `doc_continue` хотя бы один SHA изменился, отказываем до модели: «После предыдущего запуска появились новые коммиты. Запустите doc_verify для проверки текущего перевода или doc_translate для нового перевода». Даже посторонний коммит блокирует продолжение; слияние старого состояния с новыми правками не требуется.

Максимум три продолжения на исходный PR. Полные запросы и ответы моделей, результаты, замечания и SHA сохраняются в YDB на 14 дней. Модели передаётся только контекст, необходимый для текущего исправления. Если контекст отсутствует или истёк, продолжение не запускается; сообщение объясняет срок хранения и предлагает новый запуск. Недоступность YDB сообщается как ошибка хранилища, а не как истечение срока.

## 5. Критик и автоматические проверки

Общий алгоритм: **проверка → исправление → проверка → исправление → финальная проверка**. Максимум три проверки и два исправления, без дополнительных циклов для отдельных эвристик. Если ошибок нет, завершаемся раньше. После финальной проверки исправлений больше нет; оставшиеся ошибки или незавершённая проверка дают RED.

Критик получает исходный файл и текущий перевод. Проверяет сохранение смысла, полноту, отсутствие добавленных утверждений и качество языка. Возвращает «правильно» либо проблемы: файл, строки перевода, цитата, суть и ожидаемое исправление. Критик сам текст не меняет; отдельный шаг исправления получает найденные проблемы. Длинные документы проверяются соответствующими частями исходника и перевода; проверка должна охватить весь текст.

Дополнительно проверяем:

- Остаточную кириллицу в EN, включая заголовки, таблицы и подписи. Кириллица в защищённом коде — предупреждение, не повод автоматически менять код и не самостоятельная причина RED.
- Сохранность маркеров и защищённых частей, отсутствие пропавших, дублированных и оставшихся служебных маркеров.
- Корректность Markdown/YFM и сборку документации.
- Существование внутренних ссылок, якорей и assets в итоговом результате.
- Соблюдение явно заданного глоссария, если он есть.
- Полноту структуры: парсером сравниваем число блоков по типам — заголовки, абзацы, пункты списков, таблицы и их строки, блоки кода и контейнеры YFM. Перенос строки внутри абзаца не создаёт новый блок. Расхождения передаём критику: он пытается найти пропущенный, лишний или ошибочно объединённый блок, указать раздел, строки и цитату исходника, место исправления в переводе. Если локализация не удалась, показываем само расхождение без выдуманных координат. Для абзацев разница количества сама по себе не доказывает потерю текста; подтверждённые пропуски и повреждения структуры требуют исправления. Равенство количества не заменяет проверку смысла.

Область автоматических проверок ограничена файлами плана перевода и явно добавленными для них зависимостями. Проверка не обходит всё дерево документации или репозиторий, если это прямо не предписано отдельным пунктом этого контракта. «Итоговый результат» означает опубликованный кандидат для этой области, а не все существующие файлы кандидата. Ошибка вне области перевода не считается ошибкой перевода и не получает координаты «места исправления». Сравнение с исходным снимком допускается только для определения, внесён ли дефект работой; оно не расширяет область проверки. Общая ошибка сборки, которая мешает проверить выбранные файлы, даёт RED как внешний блокер с причиной, но не превращает посторонние файлы в задачи перевода.

В английской статье ссылка на русскоязычную страницу требует соответствующей английской цели. Если адрес не найден — RED с конкретной ссылкой и просьбой указать замену. В русской статье английские ссылки допустимы. Выдумывать URL или заменять `/ru/` на `/en/` без проверки цели нельзя.

GREEN возможен только после завершённой проверки критиком без ошибок и успешных обязательных автоматических проверок. Проверяем готовый неизменяемый кандидат; вердикт относится к его SHA. Любые последующие изменения требуют новой проверки.

### 5.1. Локальные исправления и отсутствие лишних повторов

После первичного перевода восстанавливаем защищённые блоки и фиксируем результат в ветке; критик проверяет именно этот кандидат. При исправлении передаём только проблемный чанк (или целый файл, если он является одной частью), его исходник, предыдущий перевод, относящиеся к нему замечания и необходимый глоссарий. Исправление пропущенной части использует её исходник и явный признак отсутствия перевода. Успешные незатронутые части повторно не переводятся. Исправления фиксируются в ветке до следующей проверки.

Критик проверяет существенные смысловые, технические и языковые ошибки; стилистические предпочтения и мелкие придирки сами по себе не блокируют слияние. Для длинных документов используются сохранённые соответствия частей. Ошибка подготовки запроса не считается выполненной проверкой или исправлением. Если исправление невозможно или кандидат остался прежним, цикл останавливается с объяснением RED; повторять тот же цикл и сборку на неизменённом SHA без нового основания нельзя. Максимум остаётся прежним: три проверки, два исправления.

Сбой сборки показывается как первичная ошибка с доступным местом и причиной. Невозможность проверить якоря из-за этого сбоя — одна зависимая неполная проверка, а не тысячи якобы сломанных ссылок. Подтверждённые ошибки ссылок отделяются от непроверенных; без сравнения с исходным состоянием нельзя утверждать, что все ошибки дерева внесены переводом. Неполнота обязательной проверки сохраняет RED, даже если диагностика сгруппирована.

## 6. Публикация и два отчёта

Полученные переводы и связанные assets сохраняются в ветке и переводном PR даже при структурных ошибках и RED: результат должен быть доступен для ручного исправления. При RED переводной PR остаётся draft. При прерывании сохраняем полученную часть и перечисляем незавершённые файлы. Если работы нет или запуск остановлен на предварительных проверках до модели, нового переводного PR нет; чистые удаления и переименования из §1 публикуются без модели.

**В исходном PR:** краткий понятный итог — что переведено, что не удалось, статус, ссылка на переводной PR и стоимость. Если запуск не состоялся — причина и необходимые действия.

**В переводном PR** (для `doc_verify` — в проверяемом): вердикт критика, SHA последнего проверенного коммита и стоимость. GREEN — перевод прошёл проверки и готов к слиянию; RED — мержить нельзя, нужны исправления. Для каждой конкретной проблемы в подробной диагностике указываем путь, строку или диапазон строк опубликованной версии, суть и что исправить руками. Для отсутствующего блока добавляем строки и цитату исходника, место вставки в переводе, если оно установлено. Если проблема не привязана к строке, например отсутствует файл, пишем это прямо.

### 6.1. Человекочитаемый результат без переполнения GitHub

В переводном PR отчёт публикуется ровно одним comment. Описание PR не создаёт и не обновляет отчёт. Этот единственный comment содержит текущий или итоговый статус, причины, необходимые действия, проверенный SHA и стоимость. Если проверки ещё не завершены, нельзя объявлять GREEN.

Оба отчёта краткие. Повторяющиеся и зависимые ошибки группируются; все конкретные подробности, полные технические логи и большие списки доступны отдельным артефактом по ссылке. Отчёт не копирует полный журнал в комментарий. До отправки проверяется допустимый размер тела GitHub; сокращение деталей не удаляет вердикт, причины, действия, SHA и стоимость. Если артефакт не удалось опубликовать, это явно сообщается, ссылка на несуществующий результат не выдаётся.

Публикация понятного состояния и стоимости не должна ожидать записи раздутого контекста. Сбои хранилища и публикации отражаются отдельно; ошибка одного отчёта не отменяет попытку опубликовать другой и не запускает повторные модельные обращения или полную перезапись неизменного контекста. Ошибка сохранения контекста явно объясняет недоступность продолжения. Учёт всех платных попыток сохраняется независимо от успеха отчёта.

## 7. Стоимость и дневной бюджет

В обоих отчётах показываем стоимость текущего запуска в рублях: перевод, проверки критиком, исправления и общую сумму. Учитываются все платные обращения, включая fallback и неудачные попытки. Стоимости всех запусков трёх режимов, в том числе RED и завершившихся ошибкой, сохраняются в той же YDB и суммируются за календарный день по Москве.

Один раз перед первым обращением к модели сравниваем накопленные расходы за сегодня с `YDBDOC_DAILY_BUDGET_RUB`. Если расходы достигли или превысили лимит, модель не запускаем: «Запуск отложен: сегодня потрачено X ₽, дневной лимит — Y ₽ (YDBDOC_DAILY_BUDGET_RUB). Повторите запуск завтра или увеличьте лимит».

Если расходы на старте ниже лимита, выполняем весь запуск, включая проверки и исправления, даже если его стоимость превысит бюджет. Превышение блокирует последующие запуски. Резервирование бюджета не требуется; параллельные запуски могут одновременно пройти проверку и суммарно превысить лимит.

## 8. Хранение в YDB

Используем одну базу для учёта запусков и стоимости (`runs`) и контекста (`run_objects`):

- `YDBDOC_YDB_ENDPOINT`: `grpcs://ydb.serverless.yandexcloud.net:2135`.
- `YDBDOC_YDB_DATABASE`: `/ru-central1/b1g7gqj2vnq67gjseuva/etns0641qf73btm7j21k`.
- Доступ сервисного аккаунта — существующий secret `YDB_SA_KEY`.
- Контекст в `run_objects` хранится 14 дней (TTL по `created_at`).

### 8.1. Компактный контекст и чтение больших объектов

Сохраняем явную структуру данных для продолжения: выбранные исходники и переводы, карту защищённых блоков, идентификаторы и границы чанков, их статусы, замечания, SHA, ссылки на обращения и стоимость. Полное дерево или индекс репозитория, временные рабочие объекты и повторные копии всего результата в контекст не входят.

Каждый полный запрос и ответ модели хранится один раз; остальные записи ссылаются на него по идентификатору. Изменение итогового статуса, ошибки публикации или метаданных не переписывает неизменённые тексты и ответы. Размер контекста растёт с объёмом выбранных документов и фактических обращений, а не с числом посторонних файлов репозитория. Примеры «два файла, восемь запросов, 300–400 КБ» не являются фиксированными лимитами или обещанием стоимости.

Крупные объекты читаются ограниченными страницами/частями с учётом лимита результата YDB, без запроса всего объекта одной выдачей. Сохраняются TTL 14 дней, полные запросы и ответы (включая неудачные платные попытки), корректность учёта и возможность продолжения. Удаление производственной базы не является способом исправления этого дефекта.

## 9. Тестирование и приёмка

Весь описанный функционал покрывается автоматическими тестами: успешные сценарии, ошибки и граничные случаи. Для всех трёх режимов нужны сквозные тесты полного процесса, включая публикацию, отчёты, сохранение контекста и учёт стоимости. Тесты запускаются в CI; изменение принимается, когда они проходят. Исправление бага сопровождается воспроизводящим его тестом. В обычном CI ответы модели имитируются, чтобы тесты были воспроизводимыми и не требовали платных вызовов.

### 9.1. Обязательные регрессии по PR 53522

Проверяем ответы с `finish_reason=length`, пустым переводом и непустыми рассуждениями; пропуски чанков и сохранность их соответствия; исправление только проблемных частей; отсутствие повторных проверок неизменённого кандидата; группировку последствий неуспешной сборки; большой набор диагностик без превышения лимита GitHub; стоимость и понятное описание PR при сбое отчёта/хранилища; постраничное чтение объекта больше лимита одной выдачи YDB; отсутствие индекса всего репозитория и копий запросов/ответов в контексте. Сбой сохранения или публикации не приводит к повторным платным обращениям и двойному учёту.

Масштабные фикстуры должны воспроизводить характер инцидента: два выбранных документа при большом дереве репозитория и тысячи зависимых диагностик. Проверки парсеров, сохранности текста и интеграций переиспользуются. Тесты отменённого поведения удаляются либо заменяются проверками этих требований, а не сохраняются ради зелёного CI. Автотесты не заменяют отдельной проверки совместимости реальных параметров провайдера; ограничения фактической приёмки перечисляются явно.
