# Проверка перевода

Проверяй translation PR по трём независимым сигналам: собственное ревью,
``doc_verify`` и CI. Не подменяй один сигнал другим и не объединяй critic со
сборкой.

## Вход

Нужна ссылка или номер translation PR в ``ydb-platform/ydb``. Исходный PR найди
в body (`Auto-generated translation for ...`) или в ветке
``ydbdoc-review/pr-<source-number>``.

## 1. Зафиксировать текущую ревизию

Получить состояние PR, ``headRefOid``, список файлов, mergeability, labels и
checks. Все дальнейшие доказательства должны относиться к этому head SHA.

Если head изменился во время проверки, начать проверку critic и CI заново на
новом SHA.

## 2. Провести независимое ревью

Это отдельная проверка, а не пересказ critic report.

1. Получить полный список и diff файлов исходного PR и translation PR.
2. Определить реальный переводимый scope:
   - RU-only изменения требуют соответствующих EN-изменений;
   - уже двуязычные изменения исходного PR не нужно переводить повторно;
   - чистые переезды, redirects и одинаковые RU/EN изменения не означают, что
     translation PR должен повторить каждый файл source PR;
   - навигационные ``toc*.yaml`` сравнивать по структуре, порядку и href;
   - отдельно объяснить любые ручные build-fix файлы в translation PR.
3. Для каждой ожидаемой пары самостоятельно сравнить смысл RU и EN:
   - факты, условия, отрицания, числа, параметры и примеры сохранены;
   - ссылки, anchors, include/directives, код и имена параметров корректны;
   - новые и удалённые разделы отражены;
   - нет пропущенных файлов из реального source scope;
   - TOC ведёт на существующие страницы и сохраняет нужный порядок.
4. Не блокировать мерж из-за вкусовых формулировок и мелких стилистических
   различий. Блокировать смысловые потери, ошибки, сломанные ссылки, неверную
   навигацию и неполный scope.

Если независимое ревью нашло блокер, итог сразу «нельзя мержить». Не публиковать
review-комментарии и не менять PR, если пользователь отдельно этого не просил.

## 3. Проверить critic

Найти последний комментарий ``ydbdoc-review`` и соответствующий workflow
``ydbdoc-review (doc_verify label)``.

Critic считается валидным только если:

- рекомендация: ``🟢 можно мержить``;
- workflow завершился успешно;
- ``Checkout`` в отчёте совпадает с текущим head SHA по префиксу;
- после отчёта не было новых коммитов.

Старый зелёный отчёт на предыдущем SHA не учитывать. Красный или отсутствующий
актуальный отчёт означает «нельзя мержить» независимо от мнения проверяющего.

## 4. Проверить сборки

Critic не должен учитывать сборку. Проверяй CI отдельно на текущем head SHA:

- ``Build documentation / build-docs`` должен быть зелёным;
- обязательные ``PR-check`` jobs и integrated status должны быть зелёными;
- skipped jobs не считать падением, если они не применимы;
- required pending, cancelled или failed status означает, что сигнал CI ещё не
  позволяет мержить.

При падении открыть ``--log-failed``, найти первую содержательную ошибку и
отличить дефект перевода от source/build-инфраструктуры. Например,
``File is not declared in toc`` может исходить из уже смерженного RU-файла и не
делает зелёный critic ошибочным. Но до исправления и зелёного rerun общий
merge-вердикт остаётся отрицательным.

## 5. Проверить mergeability

Убедиться, что GitHub сообщает ``MERGEABLE``. ``BLOCKED`` допустим только когда
причина состоит в обязательном human review. Конфликт, failing required check
или иной технический blocker означает «нельзя мержить».

## Итоговый вердикт

Разрешай мерж только при одновременном выполнении всех условий:

1. независимое ревью не нашло блокеров;
2. актуальный critic зелёный на текущем SHA;
3. актуальные обязательные сборки зелёные;
4. PR технически mergeable.

Ответ должен быть коротким и проверяемым:

```markdown
Вердикт: 🟢 можно мержить / 🔴 нельзя мержить.

- Независимое ревью: [результат и краткое объяснение scope].
- Critic: [цвет, SHA и ссылка на отчёт].
- Сборка документации: [статус и ссылка].
- Остальные обязательные проверки: [статус и ссылка].
- Mergeability: [состояние и причина BLOCKED, если есть].
```

Не мержить PR самостоятельно. Дать пользователю однозначный сигнал и привести
ссылки на доказательства.
